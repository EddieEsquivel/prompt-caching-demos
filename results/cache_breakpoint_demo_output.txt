  System prompt: 6210 chars  |  Test messages: 5

  The static system prompt (safety-classifier instructions) is identical
  across every classification request. Caching it avoids re-encoding it
  on each call, cutting time-to-first-token and input-token cost.


────────────────────────────────────────────────────────────────────────
  MODEL: gpt-5.6-sol  |  Strategy: prompt_cache_breakpoint (Responses API)
────────────────────────────────────────────────────────────────────────
  The static system prompt is marked with prompt_cache_breakpoint mode='explicit'.
  After the first call the server caches that prefix; subsequent calls skip
  re-encoding it — only the short user message is processed.

────────────────────────────────────────────────────────────────────────
  MODEL: FW-Kimi-K3-3  |  Strategy: prompt_cache_key (Chat Completions)
────────────────────────────────────────────────────────────────────────
  prompt_cache_key names the cache bucket for the system-prompt prefix.
  Every request carrying the same key reuses the cached KV state — no
  sticky routing or header changes needed. Direct analogue of GPT's
  prompt_cache_breakpoint, expressed as a body field.

  NOTE: The Microsoft Foundry gateway does not surface cached_tokens in the
  usage response for this model. Cache hits appear as latency reduction
  vs the cold baseline.

  Cache key (stable per classifier version): safety-classifier-v1

════════════════════════════════════════════════════════════════════════
  CACHE PROOF — TTFT (Time To First Token) via streaming
════════════════════════════════════════════════════════════════════════
  Message (fixed): "Where can I buy fresh vegetables near downtown Buenos Aires?"
  Runs per condition: 4

  Method: stream the same message under two conditions:
    COLD — unique prompt_cache_isolation_key per call forces a fresh
           prefill every time, preventing any implicit caching.
    WARM — same prompt_cache_key on every call shares the cached prefix.

  TTFT isolates prefill time. Total latency adds generation on top.
  A lower TTFT on WARM calls is unambiguous proof cache is active.

────────────────────────────────────────────────────────────────────────
  SUMMARY: Caching strategy comparison
────────────────────────────────────────────────────────────────────────
  Feature              |  GPT-5.6-sol                      |  FW-Kimi-K3-3                
  ────────────────────────────────────────────────────────────────────────────────────────
  API                  |  Responses API                    |  Chat Completions            
  Caching mechanism    |  prompt_cache_breakpoint field    |  prompt_cache_key body field 
  Explicit breakpoint  |  Yes — marks boundary in content  |  Yes — names the cache bucket
  Client change        |  Add field to each request        |  Add field to each request   
  Cache scope          |  Server-managed (24h retention)   |  Server-managed KV cache     
  Cold call            |  Full prompt encoded              |  Full prompt encoded         
  Warm call            |  Prefix skipped (cached tokens)   |  Prefix from KV cache        
  Cost saving          |  ~50% off cached input tokens     |  ~50% off cached input tokens

  Takeaway for this classifier workload / Kimi-K3-3:
  ─────────────────────────────────────────────────────────────────────
  prompt_cache_key is the Fireworks equivalent of prompt_cache_breakpoint.
  Set it to a stable string (e.g. 'safety-classifier-v1') in the
  request body and Fireworks caches the system-prompt prefix under that
  key — no sticky routing, no header changes, no model-side support needed.

  For this classifier workload (same system prompt, millions of short
  user messages): one shared prompt_cache_key across all classification
  requests ensures every call after the first warm write pays only for
  the short user message — same latency and cost savings as an explicit
  prompt_cache_breakpoint.
