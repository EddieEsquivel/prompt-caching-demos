  across every classification request. Caching it avoids re-encoding it
  on each call, cutting time-to-first-token and input-token cost.


────────────────────────────────────────────────────────────────────────
  MODEL: gpt-5.4-nano  |  Strategy: prompt_cache_breakpoint (Responses API)
────────────────────────────────────────────────────────────────────────
  The static system prompt is marked with prompt_cache_breakpoint mode='explicit'
  when the model supports it. After the first call the server caches that
  prefix; subsequent calls skip re-encoding it. If the model rejects the
  field, the demo falls back to implicit prefix caching (identical prefix).

  [info] gpt-5.4-nano does not support prompt_cache_breakpoint — falling back to implicit prefix caching (identical stable prefix).

  MODEL: FW-Kimi-K3  |  Strategy: prompt_cache_key (Chat Completions)
────────────────────────────────────────────────────────────────────────
  Prefix caching is automatic. prompt_cache_key routes requests that
  share it to the same replica(s), where the cached KV state lives — one
  body field, no header changes. Same outcome as GPT's
  prompt_cache_breakpoint.

────────────────────────────────────────────────────────────────────────
  SUMMARY: Caching strategy comparison
────────────────────────────────────────────────────────────────────────
  Feature              |  GPT-5.6-sol                      |  FW-Kimi-K3-3                
  ────────────────────────────────────────────────────────────────────────────────────────
  API                  |  Responses API                    |  Chat Completions            
  Caching mechanism    |  prompt_cache_breakpoint field    |  prompt_cache_key body field 
  Explicit breakpoint  |  Yes — marks boundary in content  |  No — automatic prefix match 
  Routing              |  Server-managed                   |  Key pins to same replica(s) 
  Client change        |  Add field to each request        |  Add field to each request   
  Cache scope          |  Server-managed (24h retention)   |  Server-managed KV cache     
  Cold call            |  Full prompt encoded              |  Full prompt encoded         
  Warm call            |  Prefix skipped (cached tokens)   |  Prefix from KV cache        
  Cost saving          |  ~50% off cached input tokens     |  ~50% off cached input tokens

  Takeaway for this classifier workload / Kimi-K3-3:
  ─────────────────────────────────────────────────────────────────────
  prompt_cache_key is the Fireworks equivalent of prompt_cache_breakpoint.
  Set it to a stable string (e.g. 'safety-classifier-v1') in the
  request body; requests sharing the key route to the same replica(s),
  where the system-prompt prefix is already cached. No header changes.

  Production scale (millions of short messages): KV cache is
  replica-local, so a single key concentrates load on a few replicas.
  Shard it into N buckets (e.g. 'safety-classifier-v1-0'..'-N') so each
  bucket warms its own replica and throughput scales out.
