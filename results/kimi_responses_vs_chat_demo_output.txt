════════════════════════════════════════════════════════════════════════
  SUMMARY: Responses API vs Chat Completions — FW-Kimi-K3-3
════════════════════════════════════════════════════════════════════════
  Feature              |  Responses API                  |  Chat Completions                    
  ──────────────────────────────────────────────────────────────────────────────────────────────
  Endpoint             |  POST /openai/v1/responses      |  POST /openai/v1/chat/completions    
  Cache field          |  prompt_cache_key (top-level)   |  prompt_cache_key (extra_body)       
  Cache bucket         |  safety-classifier-v1           |  safety-classifier-v1                
  SDK required         |  Yes — client.responses.create  |  Yes — client.chat.completions.create
  Response format      |  output[].content[].text        |  choices[0].message.content          
  Cached tkns field    |  usage.input_tokens_details     |  usage.prompt_tokens_details         
  Same backend cache?  |  Yes — shared key = shared KV   |  Yes — shared key = shared KV        

  Avg warm latency  — Responses API: 5082 ms  |  Chat Completions: 3504 ms

  Key insight:
  ─────────────────────────────────────────────────────────────────────
  Both API styles send prompt_cache_key to the same Fireworks backend.
  Same key → same replica(s). Cross-API reuse holds when both shapes
  render to the same token prefix; verify via cached_tokens.

  Choose based on your integration needs:
    • Responses API  — consistent with your GPT-5.6-sol integration;
                       same request/response shape across all models.
    • Chat Completions — OpenAI SDK convenience, easier streaming,
                         works with any OpenAI-compatible client.
  Caching behaviour, cost savings (~50% cached tokens), and latency
  reduction are identical regardless of which API you choose.
